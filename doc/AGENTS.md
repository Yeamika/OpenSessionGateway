# 文档与实现约束

## 1.阅读顺序

- 在阅读 `doc/` 下任何技术文档之前，必须先查看对应的 `design/` 文档，先理解设计理念、边界和职责划分。
- 如果没有完全对应的设计文档，至少先阅读：
  - `design/Total.md`
  - `design/plugin/design.md`
  - `design/client/xxx.md`

## 2.设计优先

- `design/` 文档用于说明理念、边界、职责和模块关系。
- `doc/` 文档用于说明代码结构、实现入口、API 和运行链路。
- 当 `doc/` 与 `design/` 的表达出现冲突时，应优先以 `design/` 的理念和边界为准，再回头修正文档或代码。

## 3.实现要求

- 所有代码实现都应符合设计理念，而不是只追求局部功能可用。
- 新增能力时，应先确认其是否符合现有设计边界，再决定落点和实现方式。
- 不应通过绕过设计边界的方式堆叠功能。

## 4.当前核心理念

- OSG 提供统一的信息收集、状态监视和控制入口。
- Session 由客户端托管，OSG 不作为 Session 的权威存储。
- 服务端插件负责扩展控制面，不替代客户端内部状态机。
- 客户端负责维护真实 runtime、session、permission、question 状态，并响应 OSG 的控制命令。

## 5.实践规则

- 修改服务端插件相关代码前，先阅读 `design/plugin/`。
- 修改客户端接入相关代码前，先阅读 `design/client/`。
- 修改整体架构、路由、协议和控制边界相关代码前，先阅读 `design/Total.md`。
- 写实现文档时，不要背离设计文档中的边界定义。
