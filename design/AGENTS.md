# 设计文档约束

## 1.定位

- `design/` 只说明上层理念、边界、职责和模块关系。
- `design/` 不负责展开代码入口、API 字段、具体参数名和低层协议细节。
- 具体实现、接口、字段和运行链路应写在 `doc/`。

## 2.表达原则

- 设计文档优先讲“为什么”和“边界”，而不是讲“具体怎么传”。
- 可以在必要时引入少量稳定名词，例如：
  - `c-s`
  - `s-MCP`
- 除非某个名词本身属于架构边界，否则不要在 `design/` 中写具体字段名。

## 3.禁止事项

- 不在 `design/` 中写具体 JSON 字段。
- 不在 `design/` 中写某个工具的精确参数 schema。
- 不在 `design/` 中写代码层的临时兼容策略。
- 不在 `design/` 中把控制面参数直接等同于底层运行时协议参数。
- 不在 `design/` 中默认要求继续保留旧兼容字段或旧协议壳。

## 4.推荐做法

- 如果需要描述一条链路，优先写职责分层。
- 如果需要强调约束，优先写边界规则。
- 如果需要落到具体字段或接口，把细节放到 `doc/`。
