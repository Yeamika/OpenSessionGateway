# OSG Persistence and Mailbox Notes

## Current Persistence Picture

The current OSG server uses a mixed storage model.
From code inspection, at least three distinct state layers exist:

1. PostgreSQL via Prisma
2. Redis
3. in-memory runtime/session/workspace registries

These layers do not currently appear to play the same role.

## PostgreSQL / Prisma

The Prisma schema currently defines two main models:

- `Client`
- `ClientEvent`

These tables focus on runtime/client tracking fields such as:

- UUID
- hostname
- port
- workspace
- title
- status
- heartbeat timestamps
- lifecycle event records

This suggests the relational database is intended to capture client/runtime lifecycle records and event history, not the full live runtime/session object graph.

## Redis

Redis is required by configuration and is also used by the health check path.
The server's health endpoint currently pings Redis to determine health.

That tells us Redis is considered a required runtime dependency, even if the full feature usage still needs more reading.

## In-Memory Registries

The runtime, session, and workspace registries currently live in memory.
Examples include:

- runtime registry keyed by `runtimeID`
- session registry keyed by `runtimeID::sessionID`
- workspace registry keyed by `runtimeID::workspaceID`
- caller-to-runtime binding maps
- WebSocket queue state

This means a meaningful part of OSG's live coordination model is process-local and volatile.

## What This Likely Means

The current architecture appears to separate concerns roughly like this:

- database: persistent runtime/client metadata and event records,
- redis: runtime infrastructure dependency and possibly fast shared coordination,
- memory: live connected-state coordination and runtime/session/workspace graph.

However, this is still a working interpretation, not a final conclusion.
More reading is needed before claiming the exact persistence contract.

## Mailbox System

The mailbox subsystem currently appears to be session-scoped, runtime-routed, and in-memory.

### Mailbox Item Types

Observed concepts include:

- `Notice`
- `NeedReplay`
- `QuestReply`
- `Replaied` (current code spelling)

### Mailbox Storage Behavior

Mailbox rows are stored on session bundles in memory.
There is no sign in the currently inspected mailbox code that mailbox rows are being persisted to PostgreSQL.

### Mailbox Reminder Behavior

Mailbox reminders are generated by inspecting unread and pending-reply mailbox rows and then sending a synthetic system prompt back into a target session.
That prompt looks like a mailbox summary block rather than a normal human message.
Current code schedules an initial reminder after a short delay and then keeps sending periodic reminders while unread or unreplied mail remains.

This is an important design clue: the mailbox system is not just a side channel. It can actively inject reminder prompts into sessions through the same general prompt path.

## Maintenance Implications

From a maintenance perspective, the most important current caution is this:

OSG appears to have a split brain between persistent state and live in-memory state.
That is not necessarily bad, but it means docs and operator expectations must clearly distinguish:

- what survives restart,
- what only exists while the process is alive,
- what is derived dynamically from connected runtimes.

## Still Unclear

The following points still need deeper validation:

- where Prisma writes are triggered in the runtime lifecycle,
- what Redis is used for beyond health/dependency wiring,
- whether any part of mailbox/session state is mirrored elsewhere,
- how server restart affects currently remembered runtime/session/workspace relationships.
